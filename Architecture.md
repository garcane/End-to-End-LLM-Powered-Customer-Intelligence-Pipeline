## How PBIP and PBIR fit

A Power BI Project uses a folder-based structure rather than storing everything inside one binary `.pbix` file. The semantic model and report definitions are saved as text-based files that can be version-controlled through Git. ([Microsoft Learn][1])

A simplified project might look like this:

```text
customer-intelligence-platform/
│
├── pipeline/
│   ├── etl/
│   ├── feature_engineering/
│   ├── models/
│   └── llm_insights/
│
├── database/
│   ├── schema/
│   └── migrations/
│
├── powerbi/
│   ├── CustomerIntelligence.pbip
│   │
│   ├── CustomerIntelligence.Report/
│   │   ├── definition.pbir
│   │   └── definition/
│   │       ├── pages/
│   │       ├── visuals/
│   │       └── report.json
│   │
│   └── CustomerIntelligence.SemanticModel/
│       ├── definition.pbism
│       └── definition/
│           ├── tables/
│           ├── relationships.tmdl
│           └── model.tmdl
│
├── tests/
├── requirements.txt
└── README.md
```

The exact internal folder structure can differ depending on the Power BI Desktop version, but conceptually:

* **PBIP** represents the overall Power BI project.
* **PBIR** represents the report definition: pages, visuals, filters, formatting and themes.
* **TMDL** represents the semantic model: tables, columns, measures, relationships, calculation groups and model metadata.

PBIR is publicly documented, source-control friendly and made up of structured JSON files. It can therefore be edited or generated by external development tools, although Power BI Desktop should still be used to validate the result. ([Microsoft Learn][2])

Microsoft now also supports agent-oriented tooling that can create, edit and validate reports in PBIR/PBIP format, including pages, visuals, filters, formatting and themes. ([Microsoft Learn][3])

## How the LLM layer should work

The strongest implementation would be to generate LLM insights **outside Power BI** and then store the outputs in PostgreSQL.

For example:

```sql
CREATE TABLE member_ai_insights (
    insight_id             BIGSERIAL PRIMARY KEY,
    member_id              VARCHAR(50),
    insight_type           VARCHAR(50),
    risk_level             VARCHAR(20),
    executive_summary      TEXT,
    risk_explanation       TEXT,
    recommended_action     TEXT,
    model_name             VARCHAR(100),
    prompt_version         VARCHAR(50),
    generated_at           TIMESTAMP,
    prediction_run_id      VARCHAR(100)
);
```

Your Python pipeline would:

1. Calculate churn probabilities and engagement scores.
2. Identify the relevant risk factors.
3. Pass structured results to Ollama, Gemini or another LLM.
4. Validate the response.
5. Save the generated text in PostgreSQL.
6. Refresh the Power BI semantic model.

Power BI would then display:

```text
Member: 001245
Churn Risk: 82%
Risk Category: High

Explanation:
The member's engagement has declined over the previous
three months, with no event attendance and a 64% reduction
in website activity.

Recommended Action:
Send a personalised event invitation and arrange a
membership-support follow-up within the next 14 days.
```

This approach is better than trying to call Ollama directly from a DAX measure. DAX is designed to calculate values over a semantic model; it is not a general-purpose API orchestration environment.

## Static versus interactive AI insights

There are two distinct ways you could implement the AI Insight Centre.

### Recommended portfolio implementation: pre-generated insights

The pipeline periodically generates insights and loads them into PostgreSQL.

```text
Scheduled pipeline
      ▼
ML predictions
      ▼
LLM generation
      ▼
PostgreSQL
      ▼
Power BI refresh
```

This is:

* Easier to develop
* Easier to test
* More reproducible
* Less expensive
* Better for auditability
* Compatible with standard Power BI reporting

You can store the model name, prompt version and generation timestamp alongside each response.

### Advanced implementation: user-triggered insights

A user selects a member or segment in Power BI and presses a button to request a new analysis.

This would require something outside the ordinary DAX/report execution cycle, such as:

```text
Power BI
   ▼
Power Apps / Power Automate / custom integration
   ▼
Python or FastAPI endpoint
   ▼
Ollama / Gemini / other LLM
   ▼
PostgreSQL or Fabric database
   ▼
Power BI refresh
```

Power Apps can receive context-aware data selected within a Power BI report, making it one possible interface for submitting an insight request. ([Microsoft Learn][4])

Power BI also now has translytical task flows, which support adding, updating or deleting data in supported Fabric databases from within Power BI. That could eventually support a more integrated “generate recommendation” workflow, although it introduces Fabric dependencies and greater implementation complexity. ([Microsoft Learn][5])

For the first version of your portfolio project, I would not make interactive LLM generation a core requirement.

## Should you use Python inside Power BI?

You technically can use Python scripts in Power Query and Python visuals. Power BI Desktop reruns a Python data-source script when the report data is refreshed. ([Microsoft Learn][6])

However, I would avoid using Power BI’s embedded Python environment as the principal ML or LLM layer because:

* It introduces refresh and gateway dependencies.
* The Python environment must contain the required packages.
* Service execution differs from local execution.
* Python visuals are rendered images rather than fully native Power BI visuals.
* Service-side Python visuals have payload and execution limits, including a 30 MB payload limit and a one-minute execution timeout. ([Microsoft Learn][7])
* A local Ollama endpoint such as `localhost:11434` will not automatically be available to Power BI Service.

Keep Python in your proper application pipeline and give Power BI clean analytical tables.

## What PBIR gives your portfolio

PBIR does not itself make the report “AI powered.” Its value is software-engineering discipline.

It allows you to demonstrate:

* Git-based Power BI development
* Human-readable report definitions
* Version history for report pages and visuals
* Pull requests and code review
* Better merge handling
* Automated report validation
* CI/CD deployment
* Reusable themes and report templates
* Programmatic report generation
* Separation of report and semantic-model development

PBIP projects can also be deployed programmatically through supported CI/CD approaches. ([Microsoft Learn][8])

This makes your project much more compelling than providing only a `.pbix` download.

## Verdict

**Yes, it is possible, and PBIP/PBIR is arguably a better choice than Streamlit for the final stakeholder visualisation layer.**

The most credible design is:

```text
Python = ETL, modelling and LLM orchestration
PostgreSQL = persistence and analytical storage
Power BI semantic model = governed business logic
PBIR = report visualisation definition
PBIP = complete source-controlled Power BI project
GitHub = version control and portfolio presentation
```

The only part I would avoid is trying to run Ollama or generate every LLM answer directly within an ordinary Power BI visual. Generate and persist those outputs externally, then make Power BI responsible for filtering, contextualising and presenting them.
